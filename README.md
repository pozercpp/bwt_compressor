# Compressor

Архиватор файлов и каталогов на C++ с библиотекой сжатия на основе BWT, MTF,
RLE, арифметического кодирования и Хаффмана. Поддерживает несколько входных
путей, вложенные и пустые каталоги, пустые файлы и имена UTF-8. Содержимое
файлов обрабатывается блоками по 1 МиБ. Права доступа, время изменения,
символические ссылки и специальные файлы не сохраняются.

## Возможности

- Сжатие и восстановление бинарных данных: поддерживаются все 256 значений байта.
- Блоки до 1 МиБ, включая пустые блоки.
- Контейнер `BWA2` для файлов и каталогов, чтение прежнего `BWA1`.
- Бинарные блоки `BWC1` с проверкой содержимого через CRC-32.
- Проверка путей и публикация результата только после успешного завершения.
- Цепочка BWT → MTF → RLE → арифметическое кодирование или Хаффман.
- Автоматический выбор наименьшего результата с учётом таблицы кодов.
- Хранение исходных байтов, если цепочка не уменьшает размер.
- Проверка размеров, заголовка и длин серий при распаковке.

## Требования

- Linux: файловая библиотека использует `mkdtemp` и `renameat2(RENAME_NOREPLACE)`
  для закрытого временного каталога и атомарной публикации без перезаписи.

- Компилятор с поддержкой C++23 — этот стандарт указан в CMake.
- CMake 3.16 или новее.
- Система сборки, например Make или Ninja.
- Bash для запуска `run.sh`.
- Python 3.9 или новее для интеграционных тестов CLI (при `BWT_BUILD_TESTS=ON`).

## Быстрый запуск

Из корня проекта:

```bash
./run.sh
```

Скрипт собирает библиотеку, приложение и тесты в режиме Release в каталоге
`build/`, затем запускает тесты через CTest. При ошибке он завершает работу
с ненулевым кодом.

Сборка вручную:

```bash
cmake -S . -B build -DBWT_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Для сборки библиотеки и приложения без тестов укажите `-DBWT_BUILD_TESTS=OFF`.

## Использование приложения

```bash
./build/app/compressor --help
./build/app/compressor compress "output.bwa" "input.bin" "images/" "documents/"
./build/app/compressor decompress "output.bwa" "restored/"
```

**В команде `compress` архив теперь указывается первым**, затем один или несколько
входных путей. Это изменение относительно прежней версии CLI. Все команды
сжатия создают `BWA2`, в том числе для одного файла. Внутри архива каждый вход
располагается под собственным базовым именем: `documents/readme.txt`, а не
абсолютным путём исходного каталога. Два входа с одинаковым базовым именем
отклоняются, даже если находятся в разных каталогах.

Для `BWA2` выход `decompress` — новый каталог. Для старого `BWA1` это по-прежнему
новый файл: формат определяется по сигнатуре. Выходной путь не должен существовать;
существующий каталог, файл или символическая ссылка не перезаписываются.
Число потоков выбирается автоматически, пользователь его не задаёт.

Перед упаковкой собирается список записей, без содержимого файлов, и сортируется
по хранимым путям. Поэтому архив, создаваемый внутри входного каталога, не включает
самого себя. Символические ссылки (включая ссылки на каталоги), FIFO, сокеты и
другие специальные файлы отклоняются. Во время упаковки исходные файлы не следует
изменять; изменения размера обнаруживаются, но снимок файловой системы не создаётся.

Блоки одного файла обрабатываются пулом независимо и записываются по порядку.
В первой реализации файлы идут последовательно, пул создаётся на время обработки
каждого файла. В работе и ожидании записи находится не больше `2 * N` блоков,
где `N` — от 1 до 4 потоков. Содержимое всего архива в память не загружается.

При создании и распаковке используется временный каталог `.compressor-XXXXXX`
рядом с выходом, с правами `0700`. Финальное имя появляется после полной проверки
и закрытия файлов. При обработанной ошибке временные данные удаляются. При
принудительном завершении процесса временный каталог может остаться.

При извлечении запрещены абсолютные пути, компоненты `.` и `..`, пустые компоненты,
обратные слеши, двоеточия, управляющие символы и некорректный UTF-8. Родительский
каталог должен быть объявлен раньше дочерней записи. Дубликаты и конфликты
файл/каталог отклоняются. Извлечение идёт только в новый закрытый каталог;
ссылки из архива не создаются и существующее дерево назначения не обходится.

Ограничения метаданных: до 100 000 записей, до 4096 байтов UTF-8 на путь,
до 256 компонентов пути, суммарно до 64 МиБ имён. Имена и содержимое сохраняются,
время изменения, владелец и права исходных объектов — нет.

Коды завершения: `0` — успех, `1` — ошибка ввода/вывода или данных, `2` — неверные
аргументы. Диагностика ошибок выводится в `stderr`.

### Контейнер BWA2

Все многобайтовые числа записаны в little-endian. После ASCII-сигнатуры `BWA2`
идут записи:

| Тип (1 байт) | Поля |
| --- | --- |
| 1 — каталог | Длина пути (`uint32`), путь UTF-8 без завершающего нуля |
| 2 — файл | Длина пути (`uint32`), путь UTF-8, исходный размер (`uint64`), поток `BWA1` |
| 0 — конец | Количество записей (`uint64`), общий исходный размер файлов (`uint64`) |

Вложенный поток `BWA1` сохраняет прежнее представление блоков, что позволяет
использовать один и тот же код сжатия и проверки. Его завершающий размер должен
совпасть с объявленным размером файла. Пустой файл содержит пустой поток `BWA1`.
Каталоги записываются явно, включая пустые. После общей записи завершения данные
запрещены. CRC-32 относится к содержимому блоков, а не к именам записей;
контейнер не обеспечивает криптографическую защиту.

### Поток BWA1 и совместимость

Поток начинается с четырёх ASCII-байтов `BWA1`. Далее для каждого блока записаны
его длина (`uint32`) и полный блок библиотеки `BWC1`, не больше 1 МиБ + 17 байтов.
Нулевая длина завершает последовательность; после неё записан общий исходный
размер (`uint64`). Пустой поток содержит сигнатуру и два нулевых числа.
Во вложенном потоке дальше следует следующая запись `BWA2`; в самостоятельном
старом архиве дальнейшие данные запрещены.

`bwt::decompress()` по-прежнему принимает один блок `BWC1`, а не контейнер.
Старые версии приложения не могут читать `BWA2`; новая читает оба формата.

## Библиотека работы с архивами

Файловая логика вынесена в отдельную CMake-цель `compressor::archive`.
Её публичный заголовок — [`archive/archive.hpp`](src/include/archive/archive.hpp).
Основные функции:

- `archive::create(inputs, output, options)` создаёт `BWA2` из последовательности
  путей файлов/каталогов.
- `archive::extract(input, output, options)` определяет формат и извлекает `BWA2`
  в новый каталог либо старый `BWA1` в новый файл.
- `archive::compress_file` и `archive::decompress_file` сохранены для работы с
  прежним однофайловым `BWA1` на уровне API.

Все функции возвращают суммарный исходный размер файлов в байтах. Необязательный
`archive::Options` позволяет выбрать 1–4 рабочих потока. CLI использует настройки
по умолчанию: до четырёх по `hardware_concurrency`, при неизвестном значении — один.
Библиотека не пишет в консоль; ошибки передаются стандартными исключениями.

`app/main.cpp` отвечает за аргументы командной строки, справку, вывод результата
и коды завершения. Низкоуровневая библиотека `bwt::compression` сохраняет свой
API для работы с блоками байтов и используется библиотекой архивов внутри.
Пул блоков расположен в модуле `concurrency` (цель `compressor::concurrency`,
заголовок `concurrency/block_pool.hpp`). Файловая библиотека использует этот модуль
для выполнения задач; CLI напрямую к пулу не обращается.

## API и ограничения

Заголовок: [`compression/compression.hpp`](src/include/compression/compression.hpp).

```cpp
std::vector<std::byte> bwt::compress(std::span<const std::byte> input);
std::vector<std::byte> bwt::decompress(std::span<const std::byte> encoded);
```

`std::vector<std::byte>` можно передавать напрямую. Строки передаются как байты
их содержимого. Для других объектов нужна сериализация:
копирование внутренней памяти `std::vector` или `std::string` не сохраняет
их содержимое в переносимом виде.

Один вызов обрабатывает один блок. Вход `compress` больше
`bwt::max_block_size` (1 МиБ) вызывает `std::length_error`.
Некорректный блок или несовпадение CRC-32 при `decompress` вызывает
`std::invalid_argument`. Ошибки выделения памяти передаются вызывающему коду.

Результат может быть больше входа: заголовок занимает 17 байтов. CRC-32
помогает обнаруживать повреждения, но не обеспечивает шифрование или защиту
от намеренной подделки.

Приложение разбивает большие файлы на блоки и сохраняет их длины в контейнере
`BWA2` (внутри файловых потоков `BWA1`). Функция библиотеки `bwt::decompress` принимает ровно один блок,
а не несколько склеенных блоков.

## Как работает сжатие

1. **BWT** переставляет байты с помощью сортировки циклических сдвигов,
   группируя похожие контексты. Индекс исходного сдвига сохраняется в заголовке.
2. **MTF** заменяет байты их позициями в изменяемом алфавите. После обработки
   байт перемещается в начало алфавита.
3. **RLE** заменяет серии одинаковых MTF-кодов парами «длина, код».
4. Для байтов RLE-потока строятся два варианта: **адаптивное арифметическое
   кодирование** и **канонический код Хаффмана**. Выбирается меньший вариант;
   при равенстве предпочтение отдаётся арифметическому. BWT, MTF и RLE
   вычисляются один раз. Проверка обоих вариантов добавляет работу при сжатии.

При размере RLE-потока от 64 КиБ арифметическое кодирование запускается через
`std::async(std::launch::async)`, а Хаффман выполняется в вызывающем потоке.
Оба кодера читают общий неизменяемый буфер без копирования. Перед сравнением
результатов библиотека ожидает завершения задачи; исключения передаются
вызывающему коду. Для меньших RLE-потоков оба кодера выполняются последовательно,
чтобы избежать расходов на создание потока. Порог 64 КиБ — начальная настройка;
выигрыш зависит от данных и доступных процессорных ядер. Приложение обрабатывает целые блоки пулом потоков и передаёт
`CompressionOptions{.parallel_entropy = false}`, чтобы избежать вложенного
параллелизма. Внутри каждого рабочего потока кодеры выполняются последовательно.
Обычный вызов библиотеки `bwt::compress(input)` сохраняет прежнее поведение.

Если результат не меньше входа, сохраняются исходные байты. При распаковке
преобразования выполняются в обратном порядке и проверяется CRC-32.
Арифметическая цепочка обозначена режимом 3, цепочка с Хаффманом — режимом 4.
Старые режимы 1 (BWT/MTF/RLE) и 2 (BWT/MTF/арифметическое кодирование)
поддерживаются для распаковки. Порядок распаковки: соответствующий декодер
→ RLE → MTF → обратное BWT. Публичный API не изменился.

## Формат блока с Хаффманом (режим 4)

Общий заголовок `BWC1` занимает 17 байтов: сигнатура (4 байта), режим (1 байт),
исходный размер, индекс BWT и CRC-32 (по 4 байта little-endian).
После него идут:

| Смещение | Размер | Содержимое |
| --- | --- | --- |
| 17 | 4 | Размер восстановленного RLE-потока, little-endian |
| 21 | 256 | Длины кодов байтов 0…255; ноль означает отсутствующий символ |
| 277 | остаток | Биты кодов Хаффмана, от старшего к младшему в байте |

RLE-поток ограничен удвоенным исходным размером, максимум 2 МиБ. Каждая серия
в нём — положительная длина в unsigned LEB128 (до 3 байтов) и байт MTF-кода.
Канонические коды назначаются по возрастанию длины, затем значения символа.
Первый код состоит из нулей; каждый следующий получается увеличением предыдущего
на единицу и дописыванием нулей справа до новой длины.

Для единственного символа используется однобитный код 0. Для нескольких
символов требуется полное префиксное дерево; недопустимые таблицы отклоняются.
Декодер восстанавливает ровно указанное число байтов RLE, проверяет отсутствие
лишних байтов и нулевое заполнение последнего неполного байта.
Длины кодов до 255 бит поддерживаются без упаковки кода в машинное целое.

Таблица добавляет 256 байтов расходов. Режим 4 выбирается только когда весь
его блок меньше арифметического варианта и хранения без сжатия. При равенстве
с исходным размером выбирается хранение без сжатия (режим 0). Старые декодеры,
не знающие режима 4, не смогут распаковать такие блоки.

## Структура проекта

Каталоги `include` и `src` повторяют одну модульную структуру. В `compression.cpp`
остались сборка блока `BWC1`, CRC-32 и выбор энтропийного кодера; преобразования
BWT, MTF и RLE вынесены в `compression/bwt_mtf_rle`. Кодеры Хаффмана и
арифметического кодирования находятся в собственных подкаталогах.
Публичные подключения: `compression/compression.hpp` и `archive/archive.hpp`.


```text
.
├── CMakeLists.txt
├── README.md
├── run.sh
├── src/
│   ├── CMakeLists.txt
│   ├── include/

│   │   │   ├── compression.hpp
│   │   │   ├── bwt_mtf_rle/transforms.hpp
│   │   │   ├── arithmetic/arithmetic.hpp
│   │   │   └── huffman/huffman.hpp
│   │   ├── archive/
│   │   │   ├── archive.hpp
│   │   │   └── archive_internal.hpp
│   │   └── concurrency/block_pool.hpp
│   └── src/
│       ├── compression/
│       │   ├── compression.cpp
│       │   ├── bwt_mtf_rle/transforms.cpp
│       │   ├── arithmetic/arithmetic.cpp
│       │   └── huffman/huffman.cpp

    ├── cli_test.py
    ├── archive_v2_test.py
    └── archive_test_driver.cpp
```

Тесты проверяют восстановление пустых, периодических и случайных данных,
все значения байта, блоки предельного размера, повреждённые и обрезанные
блоки, неверные размеры и длины серий.

Тесты Хаффмана также проверяют известные канонические коды, таблицы с ошибками,
255-битные коды, заполнение последнего байта и выбор режима 4.

Интеграционные тесты CLI проверяют пустые и многоблочные файлы, бинарные данные,
пути с пробелами, отказ от перезаписи и обработку повреждённых архивов.
Проверки библиотечного API сравнивают архивы при 1, 2 и 4 потоках побайтно, проверяют
порядок более восьми блоков и ошибки в поздних блоках при работающей очереди.

Проверки BWA2 охватывают вложенные и пустые каталоги, имена UTF-8, несколько
входов, коллизии, ссылки, специальные файлы, опасные пути, повреждённые записи
и очистку временных данных.

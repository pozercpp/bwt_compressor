# Compressor


Архиватор файлов и каталогов на C++ с библиотекой сжатия на основе BWT, MTF,
RLE, арифметического кодирования и Хаффмана. Поддерживает несколько входных
путей, вложенные и пустые каталоги, пустые файлы и имена UTF-8. Содержимое
файлов обрабатывается блоками по 1 МиБ. Сохраняются обычные права доступа
и время изменения файлов и каталогов, внутренние символические ссылки и
hard links обычных файлов. FIFO поддерживаются по явному флагу.

## Возможности

- Сжатие и восстановление бинарных данных: поддерживаются все 256 значений байта.
- Блоки до 1 МиБ, включая пустые блоки.
- Просмотр списка и полная проверка архива без создания файлов и каталогов.
- Контейнер `BWA5` с solid-группами, метаданными и ссылками; чтение `BWA1`–`BWA4`.
- Бинарные блоки `BWC1` с проверкой содержимого через CRC-32.
- Проверка путей и публикация результата только после успешного завершения.
- Цепочка BWT → MTF → RLE → арифметическое кодирование или Хаффман.
- Автоматический выбор наименьшего результата с учётом таблицы кодов.
- Хранение исходных байтов, если цепочка не уменьшает размер.
- Проверка размеров, заголовка и длин серий при распаковке.

## Бенчмарк множества маленьких файлов

Воспроизводимый Linux-бенчмарк находится в `benchmarks/many_small_files.py`.
Он создаёт набор файлов, архивирует каталог и печатает время, размер архива,
разницу между размером архива и логическими данными, а также максимальный RSS
процесса. Например, `python3 benchmarks/many_small_files.py --files 1000 --bytes 128 --repeats 3`.
Baseline BWA4 (Release, 1 000 файлов по 128 B, 3 запуска): размер архива
209 047 B при 128 000 B исходных данных; избыток 81 047 B (81,0 B/файл);
время 0,253 / 0,230 / 0,238 с, максимальный RSS 6 652 / 6 484 / 6 488 KiB.
RSS включает сам CLI и его библиотеки, а время включает запуск процесса.

## Прогресс и статистика

Команды `compress` и `decompress` выводят прогресс в **stderr** одной обновляемой
строкой, не чаще одного раза в 200 мс (до пяти обновлений в секунду). Строка
включается только когда **и stdout, и stderr подключены к терминалу**. При
перенаправлении любого из них промежуточного вывода, `\r` и управляющих кодов нет.
После успеха в stderr всегда выводится одна строка `Statistics:`; прежнее сообщение
об успешном завершении остаётся в stdout. При ошибке итоговой строки успеха нет.
`list` и `test` статистику не печатают.

| Показатель | Единицы и смысл |
| --- | --- |
| `processed` | `B`, точное число логических байтов содержимого: при сжатии — байты блоков, уже записанных в архивный поток; при распаковке — декодированные и проверенные по CRC байты, уже записанные в выходной поток. Запись в поток не означает `fsync` на диск. |
| Общий объём и `%` | Логический объём файлов, та же база, что у `processed`. При сжатии известен после сбора списка входов; при распаковке неизвестен до успешного завершения, поэтому промежуточного процента нет. Предварительного прохода по архиву нет. |
| `time` | `s`, секунды от начала библиотечной операции по монотонным часам, включая обход входов, обработку данных, метаданные и публикацию результата. |
| `average` | `MiB/s`, `processed / time / 1048576`; средняя за всю операцию, не мгновенная скорость. При нулевом времени — 0. |
| `input` | `B`: для сжатия — суммарный логический размер входных файлов; для распаковки — размер входного архива со всеми заголовками и метаданными. |
| `result` | `B`: для сжатия — размер всего созданного архива; для распаковки — суммарный логический размер восстановленных файлов. До завершения показывается `unknown`. |

Каждое имя hard link учитывается в логических байтах отдельно; его размер
прибавляется после записи/проверки записи ссылки, без повторного кодирования
данных. Поэтому скорость при наличии hard links не равна скорости физического
ввода-вывода. Каталоги, symlinks и FIFO дают 0 логических байтов. Логические
размеры не включают место, занятое метаданными файловой системы, и не равны `du`.
Начальный размер входа предполагает отсутствие его конкурентного изменения.
Для нулевого объёма начальный процент равен 0%, итоговый — 100%; деления на ноль нет.
100% обработанных байтов само по себе ещё не означает успех проверки footer,
установки метаданных или публикации: успех подтверждает только `Statistics:`.

Библиотека ничего не печатает. Необязательный `Options::progress` принимает
`const archive::Progress&`: `processed_bytes`, `total_bytes` (optional),
`input_bytes`, `result_bytes` (optional), `elapsed` (`chrono::duration<double>`)
и `completed`. Он действует в `create`, `extract`, `compress_file`,
`decompress_file`; `test` его не вызывает. Callback выполняется синхронно в
вызывающем потоке: начальное событие после определения размера входа, событие
после каждого записанного блока или записи hard link, затем финальное событие
после успешной публикации/закрытия результата. Ограничение частоты применяется
в CLI, а не в библиотеке; время предыдущих callback включается в длительность операции.
Не сохраняйте ссылку на переданный объект и не меняйте файлы текущей операции
из callback. Исключения callback передаются вызывающему коду: до публикации
неполный результат очищается; исключение из финального callback оставляет уже
готовый результат на месте. При ошибках данных/записи финального события нет.

## Требования

- Linux: файловая библиотека использует `mkdtemp` и `renameat2(RENAME_NOREPLACE)`
  для закрытого временного каталога и атомарной публикации без перезаписи.

- Компилятор с поддержкой C++23 — этот стандарт указан в CMake.
- CMake 3.16 или новее.
- Система сборки, например Make или Ninja.
- Bash для запуска `run.sh`.
- Python 3.9 или новее для интеграционных тестов CLI (при `BWT_BUILD_TESTS=ON`).

## Быстрый запуск

Из корня проекта:

```bash
./run.sh
```

Скрипт собирает библиотеку, приложение и тесты в режиме Release в каталоге
`build/`, затем запускает тесты через CTest. При ошибке он завершает работу
с ненулевым кодом.

Сборка вручную:

```bash
cmake -S . -B build -DBWT_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Для сборки библиотеки и приложения без тестов укажите `-DBWT_BUILD_TESTS=OFF`.

## Использование приложения

```bash
./build/app/compressor --help
./build/app/compressor compress "output.bwa" "input.bin" "images/" "documents/"
./build/app/compressor decompress "output.bwa" "restored/"
./build/app/compressor list "output.bwa"
./build/app/compressor test "output.bwa"
```

**В команде `compress` архив теперь указывается первым**, затем один или несколько
входных путей. Это изменение относительно прежней версии CLI. Все команды
сжатия создают `BWA5`, в том числе для одного файла. Внутри архива каждый вход
располагается под собственным базовым именем: `documents/readme.txt`, а не
абсолютным путём исходного каталога. Два входа с одинаковым базовым именем
отклоняются, даже если находятся в разных каталогах.

Для `BWA2`/`BWA3`/`BWA4`/`BWA5` выход `decompress` — новый каталог. Для старого `BWA1` это по-прежнему
новый файл: формат определяется по сигнатуре. Выходной путь не должен существовать;
существующий каталог, файл или символическая ссылка не перезаписываются.
Число потоков выбирается автоматически, пользователь его не задаёт.

`list` выводит по строке на запись: тип (`file`, `directory`, `symlink`, `hardlink`, `fifo`), исходный
размер в байтах и путь, разделённые табуляцией. У ссылок есть четвёртое поле:
буквальная цель symlink либо путь обычного файла для hard link. Размер каталога,
symlink и FIFO — 0; размер hard link равен размеру исходного файла. В `BWA1`
имя не хранится, поэтому выводится одна запись `file` с путём `(unnamed)`, даже
для пустого файла. В `BWA2`/`BWA3`/`BWA4`/`BWA5` выводятся сохранённые пути в порядке записей.

**Просмотр списка не означает проверки содержимого.** `list` проверяет пути,
структуру контейнера, границы блоков, согласованность заявленных размеров и
итоговые счётчики, но не декодирует полезную нагрузку и не проверяет CRC.
Повреждённое содержимое может успешно пройти `list`. Записи выводятся постепенно:
при поздней ошибке часть списка уже может быть напечатана; проверяйте код завершения.

`test` полностью декодирует каждый блок, проверяет CRC, размеры, структуру,
пути и итоговые счётчики, затем выводит `Verified N bytes.`. Восстановленные
данные сразу отбрасываются. Обе команды поддерживают `BWA1`, `BWA2`, `BWA3` и `BWA4` и не
создают выходных или временных файлов и каталогов. `list` последовательно
читает архив буфером 8 КиБ; `test` использует ограниченную очередь до `2 * N`
блоков. Для проверки путей `BWA2`/`BWA3`/`BWA4`/`BWA5` хранится ограниченная таблица имён с теми же
лимитами метаданных, что и при распаковке. Содержимое целых файлов не накапливается.

Перед упаковкой собирается список записей, без содержимого файлов, и сортируется
по хранимым путям. Поэтому архив, создаваемый внутри входного каталога, не включает
самого себя. Ссылки при обходе входов не разыменовываются; пути через ссылки
в родительских компонентах входов также отклоняются. Во время упаковки исходные
файлы не следует изменять: проверяются тип, inode, размер, права и mtime файлов,
но снимок файловой системы не создаётся. Время каталогов снимается до создания staging.

Блоки одного файла обрабатываются пулом независимо и записываются по порядку.
В первой реализации файлы идут последовательно, пул создаётся на время обработки
каждого файла. В работе и ожидании записи находится не больше `2 * N` блоков,
где `N` — автоматически выбранное библиотекой число потоков (от 1 до 4).
Содержимое всего архива в память не загружается.

При создании и распаковке используется временный каталог `.compressor-XXXXXX`
рядом с выходом, с правами `0700`. Финальное имя появляется после полной проверки
и закрытия файлов. При обработанной ошибке временные данные удаляются. При
принудительном завершении процесса временный каталог может остаться.

При извлечении запрещены абсолютные пути, компоненты `.` и `..`, пустые компоненты,
обратные слеши, двоеточия, управляющие символы и некорректный UTF-8. Родительский
каталог должен быть объявлен раньше дочерней записи. Дубликаты и конфликты
файл/каталог отклоняются. Извлечение идёт только в новый закрытый каталог;
существующее дерево назначения не обходится. Родителем записи может быть только
настоящий каталог, никогда symlink, даже если его цель находится внутри архива.
Операции с файлами и очистка staging не следуют ссылкам.

Ограничения метаданных: до 100 000 записей, до 4096 байтов UTF-8 на путь,
до 256 компонентов пути, суммарно до 64 МиБ имён и текстов целей symlinks. Имена и содержимое сохраняются,
в BWA3/BWA4 также сохраняются время изменения и обычные права доступа.
Владелец, setuid, setgid и sticky bit не сохраняются.

Коды завершения: `0` — успех, `1` — ошибка ввода/вывода или данных, `2` — неверные
аргументы. Диагностика ошибок выводится в `stderr`.

### Ссылки и специальные файлы

По умолчанию сохраняются относительные symlinks, разрешающиеся внутри архива
в файл или каталог, и hard links между выбранными обычными файлами.
Цепочки symlinks и ссылки вперёд разрешены. Цель сохраняется буквально и
разрешается относительно родителя ссылки. `.` и `..` допустимы только в цели;
выход выше корня запрещён, даже если последующие компоненты вернулись бы внутрь.
Symlink раскрывается **до** обработки следующего `..`. Допускается не больше
40 ссылок в одном разрешении и 10 миллионов шагов на архив. Висячие ссылки,
циклы, абсолютные цели, цели FIFO и проход через обычный файл отклоняются.
В целях запрещены пустые компоненты, завершающий `/`, обратный слеш, двоеточие,
управляющие символы и некорректный UTF-8; лимиты длины и глубины такие же, как у имён.

FIFO сохраняет только тип, права и mtime, не данные. Для его упаковки и создания
при распаковке нужен флаг (в API — `allow_fifo`):

```bash
./build/app/compressor compress --allow-fifo output.bwa inputs/
./build/app/compressor decompress --allow-fifo output.bwa restored/
```

`list` и `test` проверяют FIFO без этого флага и без создания объектов.
Устройства, сокеты и неизвестные типы всегда отклоняются, в том числе при запуске
от root. Запрещённая запись отменяет всю операцию, без молчаливого пропуска.
Hard links на каталоги, symlinks, FIFO и внешние файлы не поддерживаются.

Распаковка создаёт каталоги и обычные файлы в закрытом staging, проверяет весь
архив и виртуальный граф ссылок, затем создаёт hard links, FIFO и symlinks.
Права и mtime обычного inode применяются один раз после создания hard links;
у symlink восстанавливается только mtime самой ссылки. Каталоги получают
метаданные последними, от дочерних к родительским. FIFO никогда не читается
как поток данных. Все родительские компоненты открываются через дескрипторы
с `O_DIRECTORY | O_NOFOLLOW`, конечные файлы — эксклюзивно без обхода ссылок.
Результат публикуется только после успеха; ошибка отменяет публикацию.

### Контейнер BWA4

Сигнатура — `BWA4`. Все числа little-endian. Запись начинается с `uint8 type`,
`uint32 path_length` и пути UTF-8 без NUL (кроме записи конца).
Обозначение `M` — прежние метаданные BWA3: uint32 права 0777, int64 секунды
Unix mtime в дополнительном коде, uint32 наносекунды < 1 000 000 000.

| Тип | Поля после пути |
| --- | --- |
| 1 — каталог | M |
| 2 — обычный файл | M, uint64 исходный размер, поток BWA1 |
| 3 — symlink | int64 секунды mtime, uint32 наносекунды, uint32 длина цели, цель UTF-8 |
| 4 — hard link | uint64 индекс ранее объявленной записи типа 2 |
| 5 — FIFO | M |
| 0 — конец | Без пути: uint64 число записей, uint64 логический размер |

Индексы начинаются с нуля и не включают конец. Hard link не имеет собственного
содержимого или метаданных; цепочки hard-link записей запрещены. При упаковке
группируются `(st_dev, st_ino)` выбранных обычных файлов, первое имя в сортировке
хранит данные, остальные — индекс. Идентификаторы inode/device в архив не пишутся.

Логический размер суммирует размеры всех обычных файлов и каждого hard-link
имени. Файл на 100 байт с двумя дополнительными именами даёт 300 логических байт,
но кодируется и проверяется один поток на 100 байт. Эта же сумма возвращается
API и выводится CLI. Остальные типы дают ноль. CRC блоков не защищает метаданные.

### Контейнер BWA3: права и время изменения (чтение)

Архивы предыдущей версии используют сигнатуру `BWA3`. Структура записей и footer совпадает
с BWA2, но **сразу после пути** каждой файловой или каталожной записи добавлены:

| Размер | Поле |
| --- | --- |
| 4 байта | `uint32` — права `mode & 0777` (rwx владельца, группы и остальных) |
| 8 байтов | `int64` — секунды Unix времени изменения, дополнительный код |
| 4 байта | `uint32` — наносекунды, от 0 до 999 999 999 |

Все числа little-endian. После метаданных файла следуют прежние `uint64` размера
и поток BWA1. У каталога дополнительных полей нет. Запись завершения не содержит
метаданных. Неизвестные версии, биты прав вне `0777` и неверные наносекунды
отклоняются, в том числе командами `list` и `test`.

Права и mtime применяются после проверки всего архива, в обратном порядке
записей: содержимое каталога извлекается прежде, чем восстанавливаются его права
и время. Это поддерживает каталоги без права записи и даже права `000` в архиве.
Исходные объекты должны быть доступны для чтения и обхода при упаковке.
Права восстанавливаются независимо от umask; владелец не восстанавливается.
Точность и диапазон времени ограничены целевой файловой системой: она может
округлять наносекунды. Ошибка установки метаданных отменяет публикацию результата.
Время доступа, ACL и расширенные атрибуты не сохраняются. Внешний каталог
назначения не является записью архива и не получает метаданные исходного корня.
Старые BWA1/BWA2 не содержат этих полей и извлекаются без восстановления метаданных.
CRC блоков не защищает метаданные контейнера.

### Контейнер BWA2 (чтение старых архивов)

Все многобайтовые числа записаны в little-endian. После ASCII-сигнатуры `BWA2`
идут записи:

| Тип (1 байт) | Поля |
| --- | --- |
| 1 — каталог | Длина пути (`uint32`), путь UTF-8 без завершающего нуля |
| 2 — файл | Длина пути (`uint32`), путь UTF-8, исходный размер (`uint64`), поток `BWA1` |
| 0 — конец | Количество записей (`uint64`), общий исходный размер файлов (`uint64`) |

Вложенный поток `BWA1` сохраняет прежнее представление блоков, что позволяет
использовать один и тот же код сжатия и проверки. Его завершающий размер должен
совпасть с объявленным размером файла. Пустой файл содержит пустой поток `BWA1`.
Каталоги записываются явно, включая пустые. После общей записи завершения данные
запрещены. CRC-32 относится к содержимому блоков, а не к именам записей;
контейнер не обеспечивает криптографическую защиту.

### Поток BWA1 и совместимость

Поток начинается с четырёх ASCII-байтов `BWA1`. Далее для каждого блока записаны
его длина (`uint32`) и полный блок библиотеки `BWC1`, не больше 1 МиБ + 17 байтов.
Нулевая длина завершает последовательность; после неё записан общий исходный
размер (`uint64`). Пустой поток содержит сигнатуру и два нулевых числа.
Во вложенном потоке дальше следует следующая запись `BWA2`/`BWA3`/`BWA4`/`BWA5`; в самостоятельном
старом архиве дальнейшие данные запрещены.

`bwt::decompress()` по-прежнему принимает один блок `BWC1`, а не контейнер.
Новая версия читает BWA1/BWA2/BWA3/BWA4. Прежние версии не читают BWA4.
Семантика BWA1/BWA2/BWA3 и режимов BWC1 0–4 не изменена.

## Библиотека работы с архивами

Файловая логика вынесена в отдельную CMake-цель `compressor::archive`.
Её публичный заголовок — [`archive/archive.hpp`](src/include/archive/archive.hpp).
Основные функции:

- `archive::create(inputs, output, options)` создаёт `BWA5` из последовательности
  путей файлов/каталогов.
- `archive::list(input, visitor)` передаёт записи `EntryInfo {path, directory, size, type, target}`
  в callback без проверки содержимого; путь для `BWA1` — пустая строка.
- `archive::test(input, options)` полностью проверяет архив, отбрасывая данные.
- `archive::extract(input, output, options)` определяет формат и извлекает `BWA2`/`BWA3`/`BWA4`/`BWA5`
  в новый каталог либо старый `BWA1` в новый файл.
- `archive::compress_file` и `archive::decompress_file` сохранены для работы с
  прежним однофайловым `BWA1` на уровне API.

Все функции возвращают суммарный логический размер файлов в байтах,
в BWA4 учитывая каждое hard-link имя. `Options::allow_fifo` (по умолчанию false)
разрешает FIFO для create/extract. `EntryType` различает пять типов; прежнее
поле `directory` сохранено. `target` заполнено только у ссылок. Управление
параллельностью выполняется внутри библиотеки: приложение автоматически использует
до четырёх потоков по `hardware_concurrency`, при неизвестном значении — один.
Пользователь не выбирает число потоков; соответствующей опции CLI нет.
Библиотека не пишет в консоль; ошибки передаются стандартными исключениями.

`app/main.cpp` отвечает за аргументы командной строки, справку, вывод результата
и коды завершения. Низкоуровневая библиотека `bwt::compression` сохраняет свой
API для работы с блоками байтов и используется библиотекой архивов внутри.
Пул блоков расположен в модуле `concurrency` (цель `compressor::concurrency`,
заголовок `concurrency/block_pool.hpp`). Файловая библиотека использует этот модуль
для выполнения задач; CLI напрямую к пулу не обращается.

## API и ограничения

Заголовок: [`compression/compression.hpp`](src/include/compression/compression.hpp).

```cpp
std::vector<std::byte> bwt::compress(std::span<const std::byte> input);
std::vector<std::byte> bwt::decompress(std::span<const std::byte> encoded);
```

`std::vector<std::byte>` можно передавать напрямую. Строки передаются как байты
их содержимого. Для других объектов нужна сериализация:
копирование внутренней памяти `std::vector` или `std::string` не сохраняет
их содержимое в переносимом виде.

Один вызов обрабатывает один блок. Вход `compress` больше
`bwt::max_block_size` (1 МиБ) вызывает `std::length_error`.
Некорректный блок или несовпадение CRC-32 при `decompress` вызывает
`std::invalid_argument`. Ошибки выделения памяти передаются вызывающему коду.

Результат может быть больше входа: заголовок занимает 17 байтов. CRC-32
помогает обнаруживать повреждения, но не обеспечивает шифрование или защиту
от намеренной подделки.

Приложение разбивает большие файлы на блоки и сохраняет их длины в контейнере
`BWA4` (внутри файловых потоков `BWA1`). Функция библиотеки `bwt::decompress` принимает ровно один блок,
а не несколько склеенных блоков.

## Как работает сжатие

1. **BWT** переставляет байты с помощью сортировки циклических сдвигов,
   группируя похожие контексты. Индекс исходного сдвига сохраняется в заголовке.
2. **MTF** заменяет байты их позициями в изменяемом алфавите. После обработки
   байт перемещается в начало алфавита.
3. **RLE** заменяет серии одинаковых MTF-кодов парами «длина, код».
4. Для байтов RLE-потока строятся два варианта: **адаптивное арифметическое
   кодирование** и **канонический код Хаффмана**. Выбирается меньший вариант;
   при равенстве предпочтение отдаётся арифметическому. BWT, MTF и RLE
   вычисляются один раз для каждого блока.

В приложении параллельно обрабатываются **целые блоки**: каждый рабочий поток
выполняет свою цепочку BWT → MTF → RLE и сравнивает результаты двух кодеров.
Внутри одного блока арифметический кодер и Хаффман выполняются последовательно,
чтобы не создавать дополнительные потоки внутри пула. Таким образом, работа
над разными блоками идёт одновременно, а готовые результаты записываются по порядку.

При отдельном вызове библиотеки `bwt::compress(input)` без внешнего пула
действует другой режим: для RLE-потока от 64 КиБ два кодера выполняются
параллельно через `std::async`, используя общий неизменяемый буфер. Для меньших
потоков данных они выполняются последовательно. Приложение отключает этот
вложенный параллелизм автоматически; пользователю ничего настраивать не нужно.

Если результат не меньше входа, сохраняются исходные байты. При распаковке
преобразования выполняются в обратном порядке и проверяется CRC-32.
Арифметическая цепочка обозначена режимом 3, цепочка с Хаффманом — режимом 4.
Старые режимы 1 (BWT/MTF/RLE) и 2 (BWT/MTF/арифметическое кодирование)
поддерживаются для распаковки. Порядок распаковки: соответствующий декодер
→ RLE → MTF → обратное BWT. Публичный API не изменился.

## Формат блока с Хаффманом (режим 4)

Общий заголовок `BWC1` занимает 17 байтов: сигнатура (4 байта), режим (1 байт),
исходный размер, индекс BWT и CRC-32 (по 4 байта little-endian).
После него идут:

| Смещение | Размер | Содержимое |
| --- | --- | --- |
| 17 | 4 | Размер восстановленного RLE-потока, little-endian |
| 21 | 256 | Длины кодов байтов 0…255; ноль означает отсутствующий символ |
| 277 | остаток | Биты кодов Хаффмана, от старшего к младшему в байте |

RLE-поток ограничен удвоенным исходным размером, максимум 2 МиБ. Каждая серия
в нём — положительная длина в unsigned LEB128 (до 3 байтов) и байт MTF-кода.
Канонические коды назначаются по возрастанию длины, затем значения символа.
Первый код состоит из нулей; каждый следующий получается увеличением предыдущего
на единицу и дописыванием нулей справа до новой длины.

Для единственного символа используется однобитный код 0. Для нескольких
символов требуется полное префиксное дерево; недопустимые таблицы отклоняются.
Декодер восстанавливает ровно указанное число байтов RLE, проверяет отсутствие
лишних байтов и нулевое заполнение последнего неполного байта.
Длины кодов до 255 бит поддерживаются без упаковки кода в машинное целое.

Таблица добавляет 256 байтов расходов. Режим 4 выбирается только когда весь
его блок меньше арифметического варианта и хранения без сжатия. При равенстве
с исходным размером выбирается хранение без сжатия (режим 0). Старые декодеры,
не знающие режима 4, не смогут распаковать такие блоки.

неизвестном объёме распаковки.

### Контейнер BWA5: solid-группы

Создание теперь пишет BWA5; чтение BWA1–BWA4 сохраняется.
Типы 0–5 соответствуют BWA4. Новый тип 6: uint32 число файлов (1–4096),
затем для каждого uint32 длина пути, путь UTF-8, M, uint64 размер.
После таблицы следует один BWA1-поток конкатенированных данных, не более
1 МиБ в распакованном виде. Все числа little-endian.
Сумма размеров обязана совпадать с размером потока. Пустые файлы занимают
запись таблицы без данных. Индексы hard links и счётчик footer считают
каждый файл группы отдельной логической записью; сама группа не считается.
Группируются только соседние обычные файлы; остальные записи закрывают группу.
Файлы больше 1 МиБ используют тип 2 и прежний блочный поток.
Память дополнительно ограничена несколькими копиями буфера 1 МиБ и таблицей
до 4096 записей; прежние общие ограничения метаданных сохраняются.
Извлечение проверяет поток до распределения данных по файлам.

Повтор того же бенчмарка после BWA5: 43 465 B, время
0,098 / 0,105 / 0,103 с, RSS 8692 / 8684 / 8608 KiB.
Размер уменьшился на 79,2%, медианное время — примерно в 2,3 раза.
Набор содержит одинаковые байты во всех файлах: выигрыш включает межфайловое
сжатие и не является оценкой одного лишь уменьшения заголовков.

### Общий пул при создании архива

Создание BWA5 использует один пул из Options::threads рабочих потоков для
всего архива. Рабочие потоки кодируют блоки разных файлов и solid-групп;
вложенный параллелизм энтропийных кодеков выключен. Основной поток читает
источники, проверяет их состояние, записывает заголовки и готовые результаты
строго в исходном порядке. Байты архива не зависят от числа рабочих потоков.

Общий предел — 2 × threads незаписанных блоков, включая выполняющиеся задачи
и готовые результаты. Перед чтением нового блока при полном лимите записывается
самый ранний результат. Метаданные без блоков также периодически сбрасываются;
буферизация не растёт с объёмом архива. При ошибке ожидающие задачи отменяются,
выполняющиеся завершаются и потоки присоединяются; staging удаляется без
публикации частичного архива. Распаковка использует прежнюю обработку потоков.
